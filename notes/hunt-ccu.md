## Correctness bugs

**1. Named prereleases lose their patch number. `/home/folk/Programs/check-updates/core/src/version.rs`, `parse_prerelease`.**
The pattern list is `["dev","post","alpha","beta","rc","a","b","c","-"]` and the dash is checked *last*. For `1.2.3-alpha.1`, `"alpha"` is found at index 6, so `base_part = "1.2.3-"`; `split('.')` yields `["1","2","3-"]`, and `"3-".parse()` fails and is swallowed by `.unwrap_or(0)`. Result: `Version { major:1, minor:2, patch:0, pre_release:"alpha.1" }`. Same for `-beta`, `-rc1`, `-dev`. Only dash-with-no-recognized-word (`1.2.3-pre`) parses correctly, so the behavior is inconsistent from one prerelease naming convention to the next.
Downstream: `DependencyResolver::calculate_severity` compares patch fields, so under `--pre-release` an update from `1.2.2` to `1.2.3-rc1` computes `severity = None` while `target` is `Some` — `has_update()` is true so the row prints, but `will_update()` is false, so `-u` refuses to write it and it is counted in the "skipped outside the selected severity" tally with no explanation. Also hits `ccu -g` where an installed binary's version in `.crates.toml` is a prerelease.
Fix direction: parse strictly as semver (find the first `-` after the numeric core, then `+`), and stop using `unwrap_or(0)` for a segment that failed to parse — that swallow is what turns a parse bug into silent wrong data.

**2. Prerelease ordering is lexicographic. Same file, `impl Ord for Version`.**
`(Some(a), Some(b)) => a.cmp(b)` orders `alpha.10 < alpha.9` and `rc.2 < rc.10`. Semver requires dot-separated identifier comparison with numeric identifiers compared numerically. Affects "latest" selection under `--pre-release` and the `matching.sort(); matching.last()` lockfile pick in `main.rs`.

**3. Cargo's single-`=` exact pin becomes an unrewritable `Complex`. `core/src/version.rs::VersionSpec::parse`, reached via `parsers/cargo_toml.rs::parse_cargo_version`.**
`parse_cargo_version` routes anything starting with `=` into `VersionSpec::parse`, which only recognizes `==` (Python style). `"=1.2.3"` matches no operator branch, then `Version::from_str("=1.2.3")` fails, so it falls through to `Ok(VersionSpec::Complex("=1.2.3"))`. `Complex` has `satisfies() == false` (so `in_range` is always `None` and the lockfile match in `main.rs` falls back to "highest overall version in Cargo.lock", which is the wrong version for any crate present at two majors) and `is_rewritable() == false` (so `-u`, `-um` and even `-uf` silently never touch it). `=1.2.3` is standard Cargo syntax; the tool quietly cannot update those deps and gives no diagnostic.

**4. The updater rewrites a crate name in *every* section of the manifest. `ccu/src/updater.rs::update_dependency`.**
It walks `dependencies`, `dev-dependencies`, `build-dependencies`, `workspace.dependencies` and every `target.*.{dependencies,dev-dependencies}` and writes `new_version` into *all* entries matching the key, with no notion of which section the `DependencyCheck` actually came from. `Dependency` carries `source_file` but not the section it was parsed from, so the information to do this correctly is simply not captured.
Concretely: `foo = "1.0"` under `[dependencies]` and `foo = "0.9"` under `[dev-dependencies]` produce two checks with different targets; each application writes *both* entries, so the dev-dependency gets force-bumped across a major (or the normal dep gets downgraded), depending on iteration order of the `HashMap<PathBuf, Vec<...>>`. Which one wins is nondeterministic across runs. This is a data-loss-class bug in the one operation that mutates the user's files.

**5. Running ccu inside a workspace member reports nothing, silently. `ccu/src/main.rs::run_project_mode` + `detector.rs`.**
The root manifest is only ever looked for at `project_path/Cargo.toml`, and `Cargo.lock` likewise (`CargoLockParser::find_and_parse`). Neither walks upward. In this very repo, `ccu/Cargo.toml` has 17 `.workspace = true` entries; `ccu ccu/` loads no workspace deps (`load_workspace_deps` is never called with the real root), so `extract_version_or_workspace` returns `None` for all of them and they are dropped with no message — the user gets "No dependencies found in Cargo.toml" or a short, misleadingly clean table. Same path also means zero installed versions, so `current` falls back to the spec's base version and severities are computed against the declared spec rather than the lock, contradicting the resolution semantics `CLAUDE.md` states ccu keeps ("compares the installed version from Cargo.lock"). Fix: discover the workspace root by walking up for a `Cargo.toml` with a `[workspace]` table, the way cargo does.

**6. `parse_github_url` accepts any host and then queries api.github.com. `ccu/src/global.rs`.**
It takes the last two `/`-separated segments of *any* URL. `https://gitlab.com/o/r`, `https://codeberg.org/o/r`, a self-hosted gitea, `https://git.sr.ht/~user/repo` all yield an `(owner, repo)` and get sent to `https://api.github.com/repos/...`. `check_github_repo` returns `None` on non-success, `check_git_updates` then omits the package from its map, and `run_global_mode` pushes a `GlobalCheck` with `has_update: false` — i.e. a non-GitHub git install is reported as up to date rather than as unknown. There is no "could not determine" state in `GlobalCheck` at all. The same silent-success-by-omission applies to GitHub rate limiting (unauthenticated compare API, no token, no 403/429 handling).

**7. `-g` progress reporting and concurrency don't match the comment.** `check_path_updates` is a synchronous function that shells out to `git fetch` for every path install, run serially, on the async runtime thread, *before* the progress bar exists — the step labelled "check ... concurrently" blocks everything, with no timeout, and hangs on any unreachable remote. `check_git_updates` is likewise a sequential `for` loop of awaits despite sitting in `tokio::join!`, and it only bumps the bar to `len` once, at the very end.

**8. Progress callback reports the spawn index, not a completion count. `ccu/src/cratesio.rs::get_packages`.**
`callback(index + 1, total)` where `index` is the enumeration position of the task that just finished. With a 5-permit semaphore, completions arrive out of order, so `pb.set_position` jumps backwards (e.g. 40 -> 7 -> 41). Should be a shared `AtomicUsize` counter.

**9. Registry failures are labelled "not found". `ccu/src/main.rs` line ~318.**
Every entry in `fetch_errors` is printed under `"Crates not found on crates.io:"`, but `get_package` pushes timeouts, 5xx, 429 rate limits and JSON parse failures into the same bucket. A rate-limited run tells the user their crates do not exist. Related: a crate whose fetch failed is dropped from `checks` entirely (`if let Some(package_info) = package_infos.get(...)`), so it vanishes from both the table and the JSON `checks` array.

**10. `--json --update` discards the result of the write.** `let _ = updater.apply_updates(&checks, args.minor, args.force)?;` then emits the full unfiltered `checks` array. A JSON consumer has no way to tell which deps were actually rewritten or which files changed — the exact information the recent commit "Report only the updates that were actually applied" added for the human-readable path. `modified_files` should be in the envelope.

**11. Non-JSON update mode prints the table headed "Dependencies updated:" *before* calling `apply_updates`.** If the write fails (read-only file, TOML parse failure) the process has already claimed success, then errors out.

**12. Workspace-inherited deps are emitted once per inheriting member plus once for the root.** `CargoTomlParser::parse` reads `[workspace.dependencies]` from the root manifest, and each member's `.workspace = true` entry also produces a `Dependency` with `source_file` pointed at the root. The display path dedupes (`seen` HashSet in `main.rs`), but the JSON `checks` array does not — a consumer of `--json` sees N near-identical entries for every shared dep. The updater also rewrites the same root line N times (harmless, but it is doing N file parses/writes' worth of redundant work in the same run).

## Contract / documentation drift

**13. `ccu/README.md` describes the `-g` JSON shape wrongly.** It says "each check includes `source` ... and source-specific fields (`latest_version`, `git_url`, `git_hash`, ..., `local_path`)". In `main.rs`, `GlobalCheckJson` flattens a `GlobalCheck` whose `package: GlobalPackage` is a *nested* object, so `source`, `git_url`, `git_hash`, `local_path` and `binaries` are under `.package.*`, not at the check level. A `jq` filter written from the README fails.

**14. "`--json` ... status messages go to stderr" (`ccu/src/cli.rs` doc comment and `ccu/README.md`) is not implemented.** Nothing in `ccu` ever writes to stderr; every status line is `println!`. It happens to be true only because each status line is individually guarded by `!args.json`. The indicatif bar does go to stderr. The guard approach is fragile — one un-guarded `println!` corrupts the JSON stream.

## Smaller smells worth flagging

- `detector.rs::is_excluded` only compares the member directory against the exclude pattern exactly; cargo excludes whole subtrees, so `exclude = ["vendor"]` does not exclude `vendor/foo`. And the gitignore filtering only applies to `auto_discover_members` — explicit glob members go through `glob::glob` with no ignore awareness, so the two discovery paths have different semantics.
- `detector.rs::expand_workspace_member` builds a glob from `project_path.to_string_lossy()`; a project path containing `*`, `?` or `[` is silently reinterpreted as a pattern.
- `cargo_toml.rs::find_line_number` re-reads the root `Cargo.toml` from disk once per inherited dep per member (O(members x deps) file reads), and its heuristic matches the first line whose trimmed text starts with the name followed by `=` or `.` — a `[features]` entry like `tokio = []` earlier in the file wins over the real dependency line. `line_number` is serialized into the JSON, so the wrong number is user-visible.
- The parser handles `[target.*.dependencies]` and `[target.*.dev-dependencies]` but not `[target.*.build-dependencies]`; the updater has the same gap. Consistently incomplete.
- `cratesio.rs` fetches the full `/crates/{name}` endpoint (entire version history, every dep) for every crate when only versions + dates are needed; the sparse index or `/versions` would be far lighter.
- `global.rs::generate_upgrade_commands` emits `cd <path> && git pull && cargo install --path .` for path installs even when `has_dirty_changes` is true, where `git pull` will refuse. And a path repo that is only dirty (0 commits behind) has `has_update: false`, so it renders as "dirty" in the table but gets no command at all.
- `VersionSpec::Complex` returning `false` from `satisfies()` interacts badly with `main.rs`'s lockfile fallback (`versions.iter().max()`): for any spec the parser could not model, ccu picks the highest version of that crate anywhere in `Cargo.lock`, which for e.g. `syn` at 1.x and 2.x is the wrong "installed" version and produces a wrong severity.

## Structural recommendation

Two of the top four bugs (#3, #4) trace to the same root: `core::VersionSpec` is a Python/PEP-440-shaped enum that Cargo requirements are squeezed into by string-prefixing in `parse_cargo_version`, and `core::Version` is a hand-rolled loose parser. Given pre-1.0 and no API-stability constraint, the right move is to stop sharing a single version model across the three ecosystems: give `ccu` a `semver`-crate-backed `VersionReq`/`Version` (which handles `=`, multi-requirement lists, prerelease ordering and build metadata correctly and for free) behind a small trait the resolver consumes, and keep the current hand-rolled enum for `pcu`/`ncu` only until they get the same treatment. That is a real rewrite of `core/src/version.rs`'s role, and I think it is worth it — it deletes findings 1, 2, 3, and the `Complex`-fallback class of problems outright rather than patching each.

Separately, `Dependency` should carry the manifest *section* it came from (and ideally a `toml_edit` path), not just `source_file` + `manifest_key`. That is the missing piece behind finding #4, and no amount of care in `update_dependency` can fix it without that information.
